# 差異比對流程

**由內而外**地找不一致，輸出一份差異報告到 `docs/`。

- **階段一：SA 內部矛盾** — 只看前端文件（SA），找它「自己跟自己打架」。
- **階段二：Mockup ↔ SA** — 拿實際畫面對前端文件，找呈現/欄位/流程差異。
- **階段三：（Mockup + SA）↔ SD** — 再把後端文件（SD）疊上來，找前後端契約差異。
- **階段四：（Mockup + SA）↔ 程式碼** — 拿現行前端實作對「畫面+前端文件」，找實作是否落實需求。

**跑哪幾個階段由使用者複選**（預設全跑）。**判讀依上列編號由內而外**——前一階段的收斂會影響後一階段怎麼判讀。但**取材可以並行**：Axure 擷取每頁約 15 秒，先用背景執行丟出去，同時讀 SPEC 與程式碼。

**本 skill 只產出報告，不修 SA/SD/程式碼。** 發現問題就寫進報告、填上建議（見〈二〉），不要順手動手改。

## 術語（本專案固定用法）

| 代號 | 指 |
|------|----|
| **SA** | 前端版本 SPEC（系統分析／畫面與前端行為）|
| **SD** | 後端版本 SPEC（系統設計／API・Entity・業務規則）|
| **Mockup** | 原型畫面——Axure 線上原型，或本機靜態 HTML（取法見〈二〉）|
| **程式碼** | 現行實作（`src/container/<模組>/<代碼>/`、`src/component/`）|

## 一、先確認範圍與來源（不確定就問）

**SA、SD、Mockup 每次由使用者提供**（檔案路徑、貼上內容、或 Axure 連結）。用 AskUserQuestion 問清楚：

- 要比哪些模組（SM120 / SM130 / SM200 …）？
- **SA 檔在哪／哪一版？SD 檔在哪／哪一版？**（同模組常有 v0.12 / v0.14 多版並存。**沒指定一定要問，不得自己挑一個最新的就跑**——這是本 skill 最不能省的一問。）
- **Mockup 從哪來？** **先 grep SA 的〈相關畫面〉表**——Axure 連結或 Prototype 路徑通常就在那裡（`grep 'axshare'`／`grep 'Mockup'`），取到就直接用。取不到才問使用者要給截圖／文字還是連結。
- **要跑哪幾個階段（一～四，可複選）？** 依所選階段決定要準備哪些來源：只有階段四要 Grep／Read `src/`；只有階段二／三／四要取畫面；只有階段三要後端文件。
  - **使用者已明示範圍就照做**（例「全部四階段」「只要一二」「比一個有 mockup 和程式碼的」），真的沒提才問。
  - **選到的階段若整個來源不存在**（例：專案內無 Mockup 檔、`src/container` 下無該模組）→ 先回報缺什麼，問使用者要補來源還是跳過。決定跳過就在報告開頭與〈結論與建議〉**標為盲區**（見〈二〉）。其餘階段照原計畫完成。

**SPEC 改版頻繁：每次都重讀當次提供的檔，結論以這次讀到的為準**；`docs/` 裡的舊報告不是本次判讀的依據。

## 二、判讀共通規則

- **最後編輯時間一律取檔案 mtime**，格式 `YYYY/MM/DD HH:mm:ss`（文件內的「變更紀錄／版本歷程」常忘了更新，以 mtime 為準）：

  ```powershell
  (Get-Item '<path>').LastWriteTime.ToString('yyyy/MM/dd HH:mm:ss')
  ```

- **SPEC 內容出現亂碼時**（UTF-8 被當 Latin-1／CP950 解，如「æ³å®é ç®」）→ 用 Read 讀原始檔取得正確 UTF-8，以原檔為準；桌面／專案內找不到原始檔就問路徑。
- **「SPEC 讀完了」用章節清單判定，不是行數。** SPEC 動輒 900 行、Read 會分頁截斷，先抽章節標題當地圖，讀到最後一章才算讀完：

  ```powershell
  Select-String -LiteralPath '<path>' -Pattern '^## ' -Encoding UTF8 | ForEach-Object { "$($_.LineNumber): $($_.Line)" }
  ```

  行數靠不住：`Get-Content | Measure-Object -Line` 不計空行，會少報三成以上（實測一份 SPEC 回報 635 行、實際 893 行，差點漏掉後六章）。
- 路徑一律用大寫磁碟機代號（`C:\...`）。本專案有過小寫 `c:\` 讓 vitest 靜默失效的前例。
- 標記：**⚠️** = 呈現／用字差異（列表即可）、**🔴** = 明確衝突需裁決（要進待裁決總表）、**✅** = 本次已當場釐清但仍記錄供追溯。每條發現都要指到**具體出處**（§章節／欄位名／API path／畫面名）。
- **盲區＝本次沒查到的地方**：沒跑的階段、擷不到的畫面、找不到的檔案都是盲區。每個盲區寫明缺什麼、為什麼缺——讀者無法從「報告沒提」分辨那是盲區還是查過相符，而這兩者的意思正好相反。
- **同一項目三方各異時記成一條**（例某欄位 Mockup 綁 A 片語、SA 定 B 代碼類別、程式碼載 C）：在**最相關的那個階段**記一條、於該條註明第三方立場，待裁決總表也只出現一次。拆成兩三條散在不同階段，會讓同一件事被當成三個問題。
- **每張發現表的最後一欄都叫「建議」**——四個階段的表與待裁決總表一律有這欄，標題就這兩個字。格子的寫法固定：**七個值之一 ＋ `——` ＋ 一句依據**（指到 §章節／欄位／API path），七格長一個樣。七個值：`SA 改`／`SD 改`／`程式碼修`／`SA↔SD 對齊`（責任方明確）、`待裁決`（需業務決定，必進待裁決總表）、`已釐清`（本次當場確認，記錄供追溯）、`不處理`（差異存在但確認可接受，寫明為什麼可接受）。**值原字照抄**，總表才彙總得起來。🔴 只能是 `待裁決` 或帶明確責任方的那四種。
- **取 Mockup**（階段二／三／四）→ 先認來源是哪一種，兩種取法完全不同：
  - **本機靜態 HTML**（SA〈相關畫面〉給的是 `..\..\Mockup\<模組>\*.html` 這類相對路徑，檔內沒有 Axure runtime）→ 直接 Read，**不必開 Chrome**。先剝掉 `<script>`／`<style>` 再讀版面（內嵌 CSS 與 base64 圖常佔九成體積）。**接著一定要讀內嵌腳本**：清單表頭、工具列、資料列多半是 JS 產生的，版面標記裡只有空的 `<thead>`／`<tbody>`，欄位定義、預設值與權限規則全在腳本內。另外，檔內 `.mk-spec` 說明區塊與行為碼對不上是常態（說明常停在舊裁決），**那本身就是階段二的一條發現**。
  - **Axure 線上原型**（axshare 連結）→ 照 `references/mockup-extraction.md` 做。

## 三、四階段比對

### 階段一：SA 內部矛盾（只看前端文件）

**只拿 SA 當事實來源**，找它自己前後不一致的地方。常見型態：

- **同名欄位、不同寫法**：型別定義區宣告 `uniformId`，範例／流程卻用 `uniform`。
- **API 範例 ↔ 表單／流程對不上**：某欄位表單有（如 `memo`），API Request 範例沒有；或反過來（新增 body 塞了「不進 body」的 `status`）。
- **新增 vs 編輯 body 不對稱**：同一份文件裡 §新增與 §編輯的欄位組成不同，語意上卻該一致。
- **章節版本落差**：§前段已改新模型、§後段仍描述舊模型。
- **引用不存在的東西**：判斷式用了 `recordStatus`，型別與預設值都沒這欄；或引用的章節、檔案根本不存在（`grep` 一下引用到的檔名再下結論）。

產出：SA 內部矛盾表 `| # | 位置(§) | 矛盾點 | A 說法 | B 說法 | 建議 |`。

### 階段二：Mockup ↔ SA（畫面對前端文件）

以階段一收斂後的 SA 為基準，逐畫面／欄位／按鈕比對 mockup：

- 查詢條件欄位、下拉選項值（例 Mockup `Y/N/P` vs SA `0/1`）、必填與顯示條件。
- 結果表欄位與順序、inline 操作欄（如「核可」欄有無）。
- 新增／編輯／檢視頁欄位、按鈕、唯讀規則。

產出：逐畫面差異表 `| 項目 | Mockup | SA | 差異 | 建議 |`。

### 階段三：（Mockup + SA）↔ SD（再納入後端文件）

把後端文件疊上來，比前後端契約，並回頭檢查 SD 自己有無內部矛盾：

- **API 契約**：同一支 API 的 Request／Response，SA 與 SD 的欄位名、型別、必填是否一致（例 SA 送 `uniform`／SD 收 `uniformId`；SA `payDocLong` string／SD Integer）。
- **讀寫路徑對稱**：寫得進、讀不回（例 save 用 `@JsonAlias("memo")` 收得到，detail 卻回 `dataRemark`，前端欄位叫 `memo` 帶不出）。同一欄在查詢、寫入、讀回三條路徑上的格式也要對（例寫入收民國年、讀回給西元）。
- **驗證是否真的生效**：前端要 checker/captcha，後端 VO 卻忽略（假授權）。
- **SD 越界指定前端怎麼實作**：SD 管的是端點契約與業務規則，前端內部決策（用哪支 hook、`useEffect` 還是 `useApi`、state 怎麼擺）不歸它定。出現這類句子就記一條、建議填 `SD 改`。**只否定那句實作指示，端點定義照收**——連端點一起判成錯的，前端會連該接的 API 都不接。
- **SD 內部矛盾**：後端常「遷移只改一半」——Entity／DDL 章節仍舊表、遷移章節與流程圖已改新表；方法名（`deleteByUniformId` vs `deleteByCompid`）、欄位存在性（`checker`／`changeTime` 一處說不遷移、業務規則仍要求寫入）對不上。**附錄的 UAT／驗收清單最容易停在舊裁決**，與正文規則相反時照它驗收會把正確實作判為不合格。

產出：契約差異表 `| API/欄位 | SA | SD | 差異 | 建議 |` + SD 內部矛盾表（格式同階段一）。

### 階段四：（Mockup + SA）↔ 程式碼（現行前端實作）

取材要連**共用層**一起看——只讀 `Index.tsx` 會把「已在共用層實作」誤判成「程式碼沒做」：

- `src/container/<模組>/<代碼>/`（`Index.tsx`／`DetailPage.tsx`／`*Modal.tsx`）
- `src/hooks/`：DM 家族查詢頁的查詢／排序／分頁／權限閘門已抽到 `useMaintenanceQuery`，API 呼叫在 `useApi`——排序回第 1 頁這類行為在 hook 裡，頁面檔看不到。
- `src/component/`：欄位必填與驗證訊息由 `InputController` 等控制器產生（SPEC 的「必填」常常就是 `required` 一個 prop）。
- `src/constant/index.tsx`：狀態／代碼類別的實際值（正反向、代碼字面）以這裡為準。
- `src/utils/`：日期與格式化（如 `mgDateUtils`）決定畫面呈現格式。

對「畫面＋前端文件」看實作是否落實需求：

- **欄位／按鈕落實**：畫面與 SA 有的欄位、操作，程式碼是否都有；漏做或多做。
- **命名／狀態值落差**：程式碼實際用的 form key、狀態代碼，是否與 SA／Mockup 一致（例 code 用 `uniformQty`、Mockup 用 STATUS_TYPE、SA 用 `uniform`／APPROVESTATUS 三方各異）。
- **空綁定／空殼**：render `{}`、`onSave={()=>{}}`、欄位 name 重複、按鈕無 handler。
- **顯示／權限條件**：`allCompany` 是否寫死、`Authorize` 權限位元是否對上畫面按鈕。

產出：實作差異表 `| 項目 | Mockup/SA 期望 | 程式碼現況 | 差異 | 建議 |`。

## 四、輸出報告（docs/）

檔名 `docs/<模組清單>_差異報告_<SA版次>.md`（如 `docs/DM260_差異報告_v0.22.md`）——**一律帶 SA 版次**，不然日後無從判斷是比對哪一版。

**一個模組一份報告**：檔名只有模組與 SA 版次兩個變數，同名檔存在就直接覆蓋，不必先問。重跑時把仍然有效的舊發現併進本次各階段表格——同一模組散成好幾份，讀的人得自己拼湊哪條還沒修。

> **`docs/` 在 `.gitignore` 內——報告與截圖都不進版控**，只存在於本機這台。同事 pull 不到，所以追溯時要拿實體檔案，不能假設「上次的報告在 repo 裡」。收尾要怎麼提醒使用者見〈五〉。

結構——**只放被選中階段的章節**，依序：

1. **比對來源**（依所選階段列對應來源表，皆兩欄；開頭註明本次跑了哪幾個階段）
   - SA 文件：`| 文件 | 最後編輯時間 |`（檔案 mtime）
   - SD 文件：`| 文件 | 最後編輯時間 |`
   - Mockup 畫面：`| 畫面 | 截圖時間 |`（截圖檔 mtime）
   - 程式碼：`| 檔案 | 最後編輯時間 |`（若跑階段四）
   - 每張來源表就是這兩欄，標題就是來源類別本身（「SA 文件」而非「SA 文件（v0.11，第 3 頁）」）——版次與頁次的資訊在檔名與各條發現的出處裡。
2. **待裁決事項總表** `| # | 事項 | 出處 | 建議 |`——🔴 集中於此。**這節是索引**：每條一句事由、指向所屬階段表、填責任方。欄位固定，不同模組的報告才排得起來比。
3. **各階段章節**（依所選，缺的不放）：階段一 SA 內部矛盾表／階段二 逐畫面差異表／階段三 契約差異表 + SD 內部矛盾表／階段四 實作差異表。
4. **結論與建議**（哪項最優先、影響範圍、動工前必先定版的阻斷點）——排優先序，逐條指回「總表 #N」。
5. **已一致、不需處理**（本次查過而各方相符者，逐項列出）——與盲區成對：這節說「查過且相符」，盲區說「沒查到」；只列問題的話，兩者都塌成「報告沒提」。

### 報告是定稿

報告會原封不動轉給 SA 與後端，寫的時候就當成**已經寄出去的文件**：

- **用字**：日常詞、完整句子。判準是整段貼進給 SA 的信裡就能直接送出。
- **內容**：只寫現在的結論。改過的地方直接改掉，整份讀起來像一次寫成。
- **一條發現只完整講一次**——在它所屬的階段表。總表與結論用指的（「階段一 #1」「總表 #2」），不複述。同一條在四個地方各寫一遍，措辭一定會漂，讀的人反而要比對哪份才是準的。

**報告完成的判準**：依本次所選階段對照上列五節逐一點名，該放的都在、不該放的沒放。其中〈已一致、不需處理〉至少涵蓋 **API 契約／狀態碼與流程／識別欄位／批次與錯誤語意** 四類（跑到的階段有觸及者），缺哪一類要寫為什麼缺。這節最容易被漏掉——問題清單寫完時看起來已經夠完整了，但那份完整感正是盲區與相符無從分辨的來源。

> **報告內互相引用一律用「階段N #M」。** 章節號會隨「跑了哪幾階段」整批位移，拿它交叉引用必然對錯——這正是本 skill 在 SPEC 裡最常抓到的那類編號殘留。

## 五、收尾

- 回報報告路徑與重點摘要，並依責任方分類列出本次的 🔴：「SA 待改」「SD 待改」「程式碼待修」「SA↔SD 待對齊」「待裁決」（只列跑到的階段所產出者）。
- 提醒報告只在本機（理由見〈四〉），問使用者要不要貼內容給相關人或另存到共享位置。
- **走過 Axure 擷取才需要收尾**：跑 `stop-chrome.ps1`（路徑照 `references/mockup-extraction.md`〈腳本位置〉組）收掉 headless Chrome，並問使用者要不要把 `CDP_OUT` 目錄下的截圖歸檔到 `docs/axure_capture/<模組>/`。讀本機靜態 HTML 沒有這一步。
